# WP03 — Reference receiver: reassembly state machine

## Changes

- `src/schcvx/receiver.py` (new):
  - `ReceiverConfig` (frozen dataclass): `delta`, `retire_l`, `max_entries_per_peer`,
    `max_bytes_per_peer`, `max_entries_global`, `max_bytes_global`, `max_count`,
    `max_frame_len`, `max_slice_len`, `authorized` — a mapping `(peer, vni) -> rule_id`
    (see "Non-obvious choices" below for why `authorized` carries the RuleID value rather
    than being a bare set).
  - Result outcomes, one frozen dataclass per name in the package spec: `DELIVERED(frame)`,
    `PENDING`, `DUPLICATE_IGNORED`, `RETIRED_DROP`, `LATE`, `ABORTED(reason)`, `MALFORMED`,
    `PEER_REJECTED`, `TABLE_FULL`, plus a `Result` union alias.
  - `Receiver(config, clock)`, `clock` a zero-argument callable returning the current time
    (no wall-clock reads anywhere in the module — fully deterministic given the same
    `clock` sequence).
    - `receive(peer, datagram, udp_checksum_ok=True) -> Result` implements DESIGN.md
      "Receiver algorithm" steps 1-5 as revised by the package spec: checksum/decode ->
      peer+VNI+RuleID authorization -> `max_count`/`max_slice_len` bounds -> retired-ID
      drop -> admission (table/byte caps) for a new Frame ID -> per-fragment consistency,
      duplicate, length, RCS, and completion handling.
    - `sweep()` expires active entries whose `now >= expiry` and purges retirement
      records whose `now >= retire_until`, freeing their table slot.
    - `counters` dict with exactly the eight keys named in the spec: `completed`,
      `expired`, `late`, `duplicate`, `integrity_failure`, `malformed`,
      `peer_admission_failure`, `table_exhaustion`.
- `tests/test_receiver.py` (new): 33 tests covering every case the package spec lists —
  two peers with different slice lengths; both arrival orders for N=2 and N=3; every
  single-fragment loss for N=2 and N=3 (parametrized, 5 cases); identical and conflicting
  duplicates; inconsistent count, unequal nonfinal lengths, and final-longer-than-nonfinal
  in both arrival orders; bytes-over-`max_frame_len` abort; bad RCS; deadline equality
  (`t == expiry`); no delivery after expiry (including via a completing fragment that
  arrives late); sweep-driven expiry with no new fragment; late arrival after retirement;
  retirement-record expiry after `L` (table slot recovery); table exhaustion by entry
  count (with recovery after `sweep()`) and by byte cap; unauthorized peer, unauthorized
  VNI, and wrong RuleID; malformed input (zero/false checksum, short datagram, count over
  `max_count`, slice over `max_slice_len`); and a counters-shape check.

## Non-obvious choices

- **RuleID lives inside `authorized`, not as a separate config field.** The package
  spec's `config` field list is `(delta, retire_l, max_entries_per_peer,
  max_bytes_per_peer, max_entries_global, max_bytes_global, max_count, max_frame_len,
  max_slice_len, authorized {(peer, vni)})` with no separate per-peer RuleID field, yet
  the behavior spec requires "RuleID must equal the value configured for the peer."
  DESIGN.md states RuleID is "configured per peer association" (one value per peer, VNI
  is a separate field within that association). I resolved this by making `authorized` a
  mapping `(peer, vni) -> rule_id` instead of a bare set of `(peer, vni)` tuples: this
  keeps the literal `(peer, vni)` key shape from the spec while using the value slot to
  carry the configured RuleID, without inventing a new top-level config field. A caller
  wanting one RuleID per peer across all its VNIs just repeats the same value for every
  `(peer, vni)` entry of that peer.
- **Table-slot accounting: one pool, shared by active entries and retirement records.**
  DESIGN.md offers two equivalent framings — "provision capacity for active and retired
  IDs at the admitted rate" or "reserve a retirement slot at admission and refuse
  admission when exhausted" — and the spec's config has a single `max_entries_per_peer`
  / `max_entries_global` pair, not a separate retirement-pool size. I implemented a
  single slot counter per peer and globally that is incremented when a Frame ID is first
  admitted and decremented only when its eventual retirement record is purged by
  `sweep()` (after `retire_l`). This directly realizes "reserve a retirement slot at
  admission" with the only capacity numbers the config provides, and is exercised by
  `test_table_exhaustion_per_peer_and_recovery` (a completed, retired frame keeps
  occupying its slot — and keeps returning `TABLE_FULL` for a new ID — until `sweep()`
  runs past `retire_l`).
- **Receiver-wide byte caps (`max_bytes_per_peer`/`max_bytes_global`) are checked per
  incoming unique slice, not only at entry creation.** DESIGN.md step 1 lists "cap
  incomplete entries and retained bytes per peer and globally" as a pre-allocation
  check, but retained bytes keep growing for the life of an incomplete entry, so I apply
  the cap on every new (non-duplicate) slice a fragment would add — for a brand-new Frame
  ID this is checked before the entry object is created at all, so a rejection here
  "creates no deliverable state" per DESIGN.md, exactly as for the entry-count cap.
  Exceeding this receiver-wide cap drops only that one fragment as `TABLE_FULL`
  (`table_exhaustion` counter) and leaves any already-open entry pending; this is
  distinct from a byte count exceeding the per-frame `max_frame_len`, which is a
  protocol-level abort (`ABORTED`, `integrity_failure` counter) per DESIGN.md step 3.
- **All `ABORTED` reasons are counted under `integrity_failure`.** The counters list has
  no generic "aborted" bucket; DESIGN.md's RCS/length failures at completion map
  naturally to `integrity_failure`, and I extended that same bucket to every other
  protocol-level abort reason (conflicting duplicate, inconsistent count, unequal
  nonfinal lengths, final-longer-than-nonfinal, bytes over `max_frame_len`, invalid total
  length) since they are all "the reassembly state is self-inconsistent" failures with no
  better-fitting counter among the eight given.
- **A single fragment's payload can never by itself exceed `max_frame_len`.** This relies
  on DESIGN.md's statement that the receiver's maximum slice length is "at most the
  configured maximum frame length" as an operator-held configuration invariant
  (`max_slice_len <= max_frame_len`); the code does not re-validate this relationship
  between the two config fields. If a deployment configures `max_slice_len >
  max_frame_len`, a single oversized first fragment would be admitted (consuming a table
  slot) and then aborted via the `max_frame_len` check on the very next fragment attempt
  for that ID — correctness is preserved, just not the "no deliverable state on day one"
  framing DESIGN.md reserves for pre-admission drops.
- **Lower bound of the "configured frame-length range" at completion is "nonempty"
  (`>= 1`).** `ReceiverConfig` (matching the package spec's field list) carries only
  `max_frame_len`, no minimum. WP02's `fragment_frame` resolved the analogous ambiguity
  in its own bounds the same way; I kept the two reference-model halves consistent.

## Questions

None — DESIGN.md's "Receiver algorithm" section together with the package spec's
explicit revisions (no original-length field, `udp_checksum_ok=False`/zero-checksum
dropped as malformed, `t >= expiry` deadline rule, lazy-expire-on-receive-and-count-late,
reserve-retirement-slot-at-admission) fully determined the behavior. The choices above
are documented because they fill gaps the spec left open (how `RuleID` attaches to
`authorized`, how the two capacity framings map onto one set of config fields, and which
single counter absorbs every `ABORTED` reason), not because anything was blocking.
