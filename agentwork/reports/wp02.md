# WP02 — Reference sender: budget and slicing

## Changes

- `src/schcvx/sender.py`:
  - `vxlan_frame_budget(pmtu, h_ip)` = `pmtu - h_ip - UDP_LEN - VXLAN_HDR_LEN`.
  - `slice_budget(pmtu, h_ip)` (C) = `pmtu - h_ip - UDP_LEN - HEADER_LEN - RCS_LEN`.
  - `Fits` (frozen dataclass, no fields) — distinct result when the frame already fits
    standard VXLAN.
  - `Drop(reason: str)` (frozen dataclass) — distinct result for every rejection case.
  - `fragment_frame(frame, *, vni, frame_id, pmtu, h_ip, max_frame_len, max_fragments) ->
    list[bytes] | Fits | Drop`, checked in this order:
    1. `len(frame) <= vxlan_frame_budget(pmtu, h_ip)` → `Fits()`.
    2. `C <= 0` → `Drop("slice budget is not positive")`.
    3. frame length `< 1` or `> max_frame_len` → `Drop("frame length outside configured
       range")`.
    4. `N = ceil(len(frame) / C)` outside `2..max_fragments` → `Drop("fragment count
       outside configured range")`.
    5. Otherwise, build `N` `Fragment`s via `wire.encode`: all slices are `C` bytes except
       the final one (remainder of the frame), RCS = `crc32c(frame)` set only on the
       final fragment, returned as encoded datagrams in ascending index order.
  - `pmtu` (and `h_ip`, `max_frame_len`, `max_fragments`) are required keyword-only
    parameters with no default anywhere in the module, per DESIGN.md "no default [PMTU]
    in this document".
- `tests/test_sender.py`: 23 new tests, including the DESIGN.md-pinned numbers (PMTU 1500,
  no options: VXLAN budgets 1464/1444, slice budgets 1454/1434; a 1514-byte IPv4 frame ->
  slices 1454/60, outer IP lengths 1496/106), exact-fit and one-byte-over for IPv4 and
  IPv6, a 1518-byte tagged frame (accepted and rejected depending on `max_frame_len`), a
  PMTU change between two calls on the same frame, PMTU parametrization at 1280 (IPv6
  minimum)/1500/9000 with the "every emitted IP packet <= PMTU" invariant checked via
  `h_ip + 8 + len(datagram) <= pmtu`, a 10000-byte frame at PMTU 9000, the rejection when
  the minimum PMTU (1280, IPv6) cannot carry `max_frame_len` in `max_fragments` slices,
  the `C <= 0` and frame-length-range drop branches, ascending index/vni/frame_id/count on
  every fragment, and that non-final slices are exactly `C` bytes.

## Non-obvious choices

- Returning `Fits()` is checked before the `C <= 0` check, so a frame that already fits
  standard VXLAN never gets rejected for an unrelated degenerate PMTU/H_IP combination
  that would make the *fragmentation* budget non-positive — fragmentation parameters are
  irrelevant when no fragmentation is needed.
- `N < 2` is unreachable by construction and therefore untested directly: `slice_budget`
  is always exactly 10 bytes smaller than `vxlan_frame_budget` for the same `(pmtu,
  h_ip)` (`14 (header) + 4 (RCS) - 8 (VXLAN header) = 10`), so any frame that fails the
  `Fits` check (length > VXLAN budget) also exceeds `C`, forcing `N >= 2`. The `N <
  max_fragments` bound is still enforced in code per the package spec's "N outside
  2..max_fragments" wording, just not independently exercised.
- DESIGN.md's "frame length outside range" has no explicit lower bound parameter in the
  `fragment_frame` signature (only `max_frame_len`), so the lower bound is taken as
  nonempty (`>= 1`); an empty frame is in practice caught earlier by the `Fits` branch
  (0 <= budget) rather than by this check, for any configuration with a non-negative
  VXLAN budget.
- Drop reason strings (`"slice budget is not positive"`, `"frame length outside
  configured range"`, `"fragment count outside configured range"`) are this package's own
  choice — DESIGN.md and the package spec describe the rejection conditions but not wire
  or API-level reason text.
